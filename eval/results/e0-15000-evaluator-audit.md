## 发现与处理

|问题|证据与影响|本次处理|
|---|---|---|
|专家抓取搜索被自写异常包装提前终止|一个抓取点失败即抛出整场景拒绝；甚至此前已有可用抓取点，也可能被后续失败点否决|删除所有对 `choose_best_pose`、`choose_grasp_pose`、规划器和 `move` 的运行时替换，直接调用官方 `play_once()`|
|专家成功检查顺序与官方不同|旧封装先检查再 `close_env(clear_cache=True)`；官方先 `close_env()` 再检查。本次没有证据量化这项差异对旧成绩的影响|恢复官方顺序，并在同一个任务对象上重新 `setup_demo`，保留专家创建的任务属性|
|环境关闭异常可能被当作正常回合|旧 `finally` 只写 `close_error`，正常状态可能继续占名额|关闭失败记为运行错误，保存原状态与异常，停止继续采样|
|场景参数存在硬编码与计数耦合|机器人路径固定写为 Aloha；`now_ep_num` 使用候选编号；模板数量绑定初始 seed 列表。当前 E0 恰好是 Aloha、5 seeds，未证明这些造成了旧成绩错误|从官方 embodiment/camera 配置解析；回合编号按完成策略数；模板数量明确绑定目标回合数并落盘|
|“与官方指令 RNG 一致”的表述过强|官方模板使用 Python `random`，上游客户端没有每回合重置它；我们的历史实现按场景 seed 重置|保留已使用的确定性语言约定，隔离其 RNG 并明确记录；不声称与上游随机流逐位相同|
|五次专家配额未实现|现有逻辑要求专家通过才执行策略，持续换 seed 补足有效，20 次连续无有效才停；上游客户端同样没有赛事五次预算|列为正式恢复阻塞项；未提高 20、未继续筛 seed、未把旧结果改称比赛合规结果|

此前“没有修改官方任务文件，所以行为与官方一致”的说法不充分。自写方法替换即使不改官方文件，也会改变它的执行语义。此前的测试没有覆盖真实官方多抓取点遍历；这一遗漏属于评测端问题。

## 哪些流程复用了官方实现

修复后的 `eval_expert.py` 仅在官方任务调用外记录时间和异常。`eval_official_flow.py` 集中单回合执行顺序，`eval_dev_suite.py` 保留调度接口与证据保存：

1. 官方 `setup_demo → play_once → close_env → plan_success/check_success`。
2. 同一任务对象、同 seed 再次 `setup_demo`；用官方专家 `info` 调官方 `generate_episode_descriptions`，Clean 选 seen，Randomized 选 unseen。
3. 官方 websocket reset，然后每个动作块一次 `get_obs → infer`。输入仍只包含头部、左腕、右腕 RGB、关节状态和指令。
4. 官方 `take_action` 完成关节控制、插值、步数上限及成功判定；逐动作检查成功，不自行定义奖励、抓取成功或动作修正。

没有直接运行上游完整批处理入口，因为它还承担无限专家筛选、自动换 seed、异常跳过和自己的输出管理，无法直接满足本次固定名额、历史恢复、双卡互斥及双视角证据要求。保留的外层适配必须明确披露，不能称为“原封不动运行官方评测脚本”。

目前明确保留的差异包括：意外专家异常记录后停机（上游批处理会跳过）；每候选独立仿真进程；确定性的语言模板 seed；只读轨迹/诊断和双视角录像；策略结束后额外一次终帧观测。这些不向模型加入专家或 observer 输入，但不能仅靠 CPU 对照宣称整套数值、随机流及场景采样已与官方完全等价。

新增执行版本与恢复协议检查，旧 `protocol.json` 缺少相同流程版本时拒绝续跑。修复不能无记录地接到旧执行段；任何后续恢复仍需明确清单、输入校验与保留前缀。

## 正式恢复仍需解决的事项

五次限制按专家发起次数计，换 seed 或同 seed 重试不能清零。达到上限后仍须进行策略测试，不能继续要求专家先通过。因此需要一个独立的比赛协议适配层：明确配额属于哪一个计划测试名额，持久化每次专家发起及中断，并在五次耗尽后禁止再调用专家。这里“每名额”的映射是待核实的实现方案，不能擅自把规则中的“场景”替换成任务组或 seed。

还必须解决专家不通过时的官方指令参数和任务属性来源。部分任务的属性由 `play_once()` 创建，不能简单关闭专家开关后猜指令或补属性；需要完整验证策略入口、成功判定及场景重置。当前上游客户端没有这个五次耗尽后的独立分支，故本次没有凭空实现并声称合规。

既有 385 个完成策略回合、36 条受影响拒绝、审计及故障中断都必须保留。补充或重评受影响场景将改变已有采样历史，需要单列协议与结果，不能悄悄拼成一份“已按赛事规则完成”的 500 有效结果。当前只完成脚本修正与所述范围的验证，**尚不具备正式恢复条件**。

E0 的 BF16 保存、FP32 执行选择及 FP32 原值差异仍按[训练交接审计](e0-15000-handoff-audit.md)披露。此次没有换权重、训练、提交竞赛或 push；最终报告的本地 commit 仍待最终口径与完整评测验收。
