# E0/F1 评测前模型数值链路验收说明

> **当前状态：F1 正式训练已完成。** 现在不讨论如何开训，只做训练收尾、产物交接和 E0/F1 评测前验收。目标不是重新计算成功率，而是确认评测程序正在评测我们以为的那个模型。

## 0. 为什么突然要做这项验收

这份验收起因于我们在做失败分析时写下的一条条件性诊断：

> **如果**大量回合出现无有效动作、持续震荡或关节目标异常，就不应立即把失败解释为模型能力不足，而应先检查 checkpoint、norm、robot config 和动作反算/导出链路。

当前 `baseline_episodes.jsonl` 只能告诉我们：448 个有效策略失败运行到了任务动作上限。它没有记录“无有效动作”、“震荡”或“关节异常”这些语义标签，所以目前**尚未证明这些现象大量发生**。需要回看三相机画面、轨迹和动作记录才能判断。

这不是因为已经发现某个 norm 或动作映射用错了。只是 F1 已训练完成，在正式解读 E0/F1 成功率之前，把这条条件性诊断落成一次低成本的常规交付验收。

对 E0/F1 而言，最需要提前排除的是四类“程序可以继续运行、但动作已经错了”的静默问题：评测加载了错误 checkpoint、使用了不配套的 norm、读到了错误 robot config，或者导出/重载后的动作发生了变化。

另外，Hugging Face 上的 `training.pt` 只是可恢复训练状态，不是可独立评测的完整 6.4B HF 模型，因此交付时还必须确认评测端拿到的是完整导出。

所以这份说明是一项**正式评测前的常规交付验收**，不是对已统一模型精度规则的重新讨论。

## 1. 我们在担心什么

`52 / 500 = 10.4%` 这个除法没有发现问题。

要排除的是另一类问题：**模型权重是对的，但在变成机器人关节动作的过程中，norm、robot config 或导出权重加载错了。**

例如，模型输出一个归一化后的动作 `0.5`：

```text
使用正确 norm 反算  -> 关节目标 0.2
使用错误 norm 反算  -> 关节目标 1.8
```

第二种情况下，评测程序仍会正确记录 `success=false`。成功率没有算错，但我们会错误地把失败归因为模型能力不足。

## 2. 正式评测前必须通过的四项检查

### 2.1 checkpoint 与 norm 绑定

**主责：F1 训练同学提供绑定记录；评测同学对实际加载文件做最终复核。**

训练端提供：

- 实验 ID 和 global step；
- checkpoint 的确切路径、Hugging Face 固定 revision 和 SHA-256；
- 训练时 norm 文件及其 SHA-256；
- norm provenance 和动作表示（绝对/相对）。

评测端不能只看文件名，必须重新计算 SHA，确认：

```text
checkpoint 记录的 norm SHA
        = 交付 norm 的 SHA
        = 评测实际加载文件的 SHA
```

E0/F1 必须使用它们的 clean absolute-action norm，不能误用原始基座的官方 norm。E1 改为相对动作后必须绑定另外重算的 norm。

### 2.2 实际加载的有效配置

**主责：评测同学；F1 训练同学提供训练时的预期配置供对照。**

核对的不是“准备提交的 YAML”，而是评测进程从训练 CLI 和 robot config 最终解析出的值。E0/F1 至少确认：

```yaml
chunk_size: 50
max_action_dim: 55
arm_subtract_state: false
gripper_subtract_state: false
norm_type: bounds_99_woclip
loss_type: L1_fm
```

上述名称是验收记录中应展示的含义，以源配置的实际字段路径为准。同时确认最终物理动作为 12 维机械臂 + 2 维夹爪、字段顺序没有变，评测进程没有读到缓存或另一份配置。

### 2.3 完整 `50×14` 动作反算

**主责：评测同学；F1 训练同学提供动作字段、维度和 norm 来源。**

数值链路应为：

```text
模型输出的 normalized action：50×55
        ↓ 去 padding + 反归一化 + 动作映射
仿真器接收的 physical action：50×14
```

需要检查：

- 形状是否为 `50×14`；
- 是否存在 NaN/Inf；
- 12 维机械臂与 2 维夹爪的顺序是否正确；
- 关节目标、夹爪值和相邻步变化是否在合理范围；
- 是否出现异常大值、持续饱和或固定不动。

这一项检查可以在评测 GPU 上完成，不需要占用 A100 长训资源。

### 2.4 导出前后和重载一致性

**主责：F1 训练同学完成导出端审计；评测同学完成部署端独立加载冒烟。**

固定同一份观测、语言指令、noise、dtype 和推理后端，比较：

```text
训练内存中的模型
        ↓
导出的完整 HF 模型
        ↓
新进程重新加载的模型
```

在完全相同的数值条件下，比较完整 `50×14` 动作，记录最大绝对误差和相对误差。项目当前的重载验收标准为 `atol=rtol=1e-6`。

E0 训练端已有本地导出重载动作审计，但评测端仍需确认实际部署链路。F1 现在必须对最终候选 checkpoint 重复同一验收，不能因为长训已结束就跳过。

## 3. 谁负责什么

| 角色 | 主要责任 |
| --- | --- |
| F1 训练同学 | 立即冻结已完成的 run；交付 checkpoint、norm、config、metrics 和运行记录；回溯确认与 E0 的配置差异；完成导出前/导出后/新进程重载的动作一致性审计 |
| 评测同学 | 分别注册 E0 和 F1；核对实际下载文件的 SHA；确认两者使用相同的 norm、有效配置、dtype 和后端；运行 `50×14` 数值检查和少量仿真冒烟 |
| 实验负责人 | 冻结唯一评测协议；四项验收未通过时不启动正式 500 episodes |

这不是二选一：训练端证明“交付的模型没有在导出时变掉”，评测端证明“部署时确实按交付方式加载了它”。

## 4. F1 训练完成后的执行顺序

### 第一步：冻结 F1 run，禁止覆盖

**负责人：F1 训练同学。**

1. 记录 F1 实验 ID、最终 global step、代码 commit 和 SwanLab run ID；
2. 保留所有计划比较的 milestone checkpoint，不用最终 step 覆盖 5k/10k/15k；
3. 保存实际训练 config、数据 manifest/split、norm 及 provenance、metrics 和精度记录；
4. 每个 checkpoint 使用独立 Hugging Face 目录，记录固定 revision 和 SHA-256。

### 第二步：回溯核对 F1 是否为单变量实验

**主责：F1 训练同学；复核：实验负责人。**

F1 与 E0 应当保持以下内容一致：

```text
基座权重与 revision
数据 manifest 和 train/val split
clean absolute-action norm 及 SHA
动作表示和 loss
可训练参数范围
global batch、学习率日程和 processed samples
随机种子与 BF16/FP32 精度路径
```

唯一计划内变化应为：

```text
E0: image_augment = false
F1: image_augment = true
```

生成一份 E0/F1 配置 diff 随交接记录保存。如果发现其他差异，不要删除或重训 F1，但必须把差异显式记录；此时结果不能严格归因为 photometric 增广。

### 第三步：完成 F1 训练端导出审计

**主责：F1 训练同学；审计结果由实验负责人复核。**

1. 对计划进入开发集比较的 checkpoint 导出完整 HF 模型；
2. 使用固定观测、语言和 noise，比较导出前、导出后和新进程重载后的完整 `50×14` 动作；
3. 保存 `action-audit.json`、导出配置、实际 dtype、后端和最大误差；
4. 如果 A100 仍可访问，在释放训练环境前完成；如果已释放，则在正式评测前使用能加载该完整模型的 GPU 补做。

### 第四步：评测端用同一协议验收 E0 和 F1

**主责：评测同学；协议是否一致由实验负责人复核。**

1. 按团队已统一的精度规则执行，E0 和 F1 使用相同的评测精度和后端；
2. E0 和 F1 分别使用唯一模型 ID 注册，但必须使用同一份 clean norm、同一动作映射和同一推理配置；
3. 分别核对 checkpoint/norm SHA、有效 config、实际 dtype 和 `50×14` 动作数值；
4. 在同一少量 Clean/Randomized `task-setting-seed` 上冒烟，只排查加载和动作异常，不根据冒烟成功率下结论；
5. 将实际信息写入各自的 `checkpoint.json`、`server-runtime.json` 和冒烟报告。

### 第五步：先选 checkpoint，再跑正式评测

**主责：实验负责人冻结选择协议；评测同学按协议执行。**

如果 F1 保留了 5k/10k/15k 等多个 milestone，先在固定小开发集上使用完全相同的 `task-setting-seed` 配对比较，只让胜出 checkpoint 进入完整 500 episodes。不能先给每个 checkpoint 都跑 500 episodes，再选最高的一个。

F1 的正式结果必须与 E0 在相同的 `task-setting-seed`、dtype、后端、norm 和成功判定下比较。

## 5. 通过标准

以下条件全部满足才能启动正式评测：

- [ ] checkpoint、norm、config 都有唯一路径、revision 和 SHA；
- [ ] 已保存 E0/F1 配置 diff，确认计划内唯一变量为 `image_augment`；其他差异已显式记录；
- [ ] 评测进程的实际配置与交付记录一致；
- [ ] normalized `50×55` 能正确转换为有限、合理的 physical `50×14`；
- [ ] 导出前后和新进程重载动作一致；
- [ ] 实际 dtype、构建模式和推理后端已记入运行日志；
- [ ] 少量 Clean/Randomized 仿真冒烟没有加载、数值或动作异常。

验收不要求冒烟 episode 必须成功。冒烟的目的是确认链路正常，不是用少量场景提前判断模型效果。
