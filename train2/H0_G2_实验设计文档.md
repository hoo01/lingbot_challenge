# H0/G2 实验设计：Clean-only 完整 Action Expert

**版本日期**：2026-10-13

**状态**：实验口径与 H0-A/H0-C 工程入口已冻结；等待 2×80G 实机验收

**实验名称**：仓库侧称 `H0`，训练运行时称 `G2`

**操作手册**：[`README.md`](README.md)
**冻结配置**：H0-A [`train_h0_full_expert_2gpu.yaml`](configs/train_h0_full_expert_2gpu.yaml)、H0-C1 [`train_h0_c1_2gpu.yaml`](configs/train_h0_c1_2gpu.yaml)、H0-C2 [`train_h0_c2_2gpu.yaml`](configs/train_h0_c2_2gpu.yaml)

> 本文定义为什么做 H0、允许改变什么、必须保持什么不变，以及如何判定实验是否有效。具体安装和启动命令以操作手册为准。本文中的“通过”只表示工程或实验门槛通过，不代表模型效果已经提升。

## 一、实验决策摘要

H0 从官方允许的 `LingBot-VLA-v2-6b` 原始基座开始，使用完整 50 任务 Clean demonstration、absolute joint action 和仅由训练集计算的归一化统计，训练完整 36 层 Action Expert 及 state/action/time projections；VLM 和视觉编码器保持冻结。训练采用两卡 upstream FSDP2。15,000 optimizer steps 是与 E0 对齐的第一个完整里程碑，不预设为训练终点；如果第 10.2 节冻结的 Clean validation 窗口判据在 15k 达到至少 1% 改善，预期动作是从 15k 启动独立、可追溯的 continuation 阶段。

本轮只检验一个主要假设：

> E0 只训练 Action Expert 最后两层，动作模型可训练容量可能不足；在不改变数据、动作语义、损失和冻结主干的前提下，训练完整 Action Expert 能否改善策略学习。

因此，本轮不同时加入图像增广、状态扰动、动态指令采样、VLM 解冻、E0 warm start 或 relative action。若一次改变多个因素，即使结果改善也无法判断原因。

## 二、背景与问题定义

### 2.1 已有结果

现有开发评测提供了以下参照。历史原始基座与后续对齐评测并非同一组场景，因此分别列出，不能混作严格配对结果：

| 路线 | 主要变化 | 开发评测 | 证据 |
| --- | --- | ---: | --- |
| 历史原始基座 | 不训练；历史 500 场景 | 52/500，10.4% | [`baseline.md`](../eval/results/baseline.md) |
| 同 seed 原始基座 | 不训练；与 E0 对齐的 500 键，含 4 个超时零分 | 49/500，9.8% | [`baseline-e0-same-seed-20261010.md`](../eval/results/baseline-e0-same-seed-20261010.md) |
| E0 | absolute action；最后两层 Expert + projections | 54/500，10.8% | [`e0-15000-final.md`](../eval/results/e0-15000-final.md) |
| F1 | 在 E0 训练范围上加入 photometric augmentation | 49/500，9.8% | [`f1-15000-completed-20261012.md`](../eval/results/f1-15000-completed-20261012.md) |

这些结果说明：

1. 在现有对齐口径下，E0 相对原始基座只有小幅变化，最后两层训练尚未形成明显突破；
2. F1 没有超过 E0，当前证据不支持直接把图像增广作为下一轮主变量；
3. 下一轮更适合检验动作模型容量，而不是继续叠加数据或视觉变量。

上述分数来自队内固定开发协议，不是官方榜单成绩，也不能据此预先承诺 H0 的成功率。

### 2.2 可证伪假设

**主假设 H1**：在相同 Clean 数据、absolute action、global batch 和训练步数下，完整 Action Expert 比只训练最后两层具有更好的动作拟合与闭环表现。

**零假设 H0-null**：扩大训练范围不会带来稳定收益，甚至可能因优化难度、过拟合或灾难性漂移而退化。

**工程假设 H-eng**：2×80G GPU 上的 upstream FSDP2 能以可接受的显存和吞吐完成完整 Expert 的训练、保存、恢复与 FP32 导出。

主假设只有在模型完成冻结后的固定闭环评测中才能判断；训练 loss 下降、smoke 通过或成功导出都不能单独证明主假设成立。

## 五、数据协议

### 5.1 数据范围

- 50 个官方 RoboTwin Clean 任务；
- 每任务 50 个 demonstration，共 2,500 个 episode；
- 每任务 episode 0–44 用于训练，共 2,250 个训练 episode；
- 每任务 episode 45–49 用于验证，共 250 个验证 episode；
- instruction 只使用数据中已审计的 seen instruction；本轮不做动态替换。

Randomized 数据不得用于训练、归一化统计、checkpoint 选择或超参数选择。模型和 checkpoint 完全冻结后，才允许将 Randomized 用于最终泛化评测。

### 5.2 动作语义

输入 state 与目标 action 都是 14-D joint representation：12 个双臂关节维度和 2 个夹爪维度。运行时实际读取的 vendor `robotwin.yaml` 中，arm 和 effector action 均须满足：

```text
subtract_state: false
```

这才是 absolute action 的有效证据；配置中的 `action_mode: absolute` 只是声明，不能替代对实际 robot config 的检查。

### 5.3 Norm 口径

Norm 只使用每任务 episode 0–44 计算，不能看到验证 episode。正式训练使用 `bounds_99_woclip` 所需的 absolute-action 统计结构，包括 mean、std、q01、q02、q98、q99、min 和 max。

preflight 必须同时验证：

- manifest 明确为完整 Clean-only 50 任务；
- 数据目录、LeRobot metadata 和 parquet 文件实际存在；
- norm provenance 对应当前 manifest；
- train/validation episode 划分正确；
- norm SHA、样本数、维度、有限性和分位数顺序正确。

## 六、优化与分布式设计

| 配置项 | 正式值 |
| --- | ---: |
| GPU | 2×80G |
| 分布式策略 | upstream composable FSDP2 |
| 每 rank batch | 32 |
| world size | 2 |
| gradient accumulation | 1 |
| global batch | 64 |
| gradient checkpointing | 开启 |
| DataLoader workers | 每 rank 2 |
| learning rate | `5e-5` |
| warmup | 50 optimizer steps |
| H0-A max steps | 15,000 |
| validation interval | 250 steps |
| checkpoint interval | 500 steps |

计算关系为：

```text
global batch = 32 × 2 × 1 = 64
processed samples = 64 × 15,000 = 960,000
```

15k 与 E0 的总 processed samples 口径对齐。当前实现只批准 `world_size == 2`，DCP 也只允许在相同 world size 下恢复；本轮不设计 2 卡到 8 卡接力。

### 6.1 15k 的定位与 continuation 预案

E0 实测可训练参数为 `101,159,479`；完整 Expert 的既有 dry-run 估计约为 2.4B，约是 E0 的 24 倍。参数量比例不能线性换算所需样本数，也不能单独证明 H0 一定欠训，但它足以说明“相同 96 万 processed samples 已经充分”不是安全假设。正式模型启动日志必须记录实际 `trainable_parameters`，替换文档中的 2.4B 估计。

队内提供的 `Verse_Vv` 观察显示，其 8 卡全参路线从 12k 到 18k 时 Clean 仍提升约 2 个点。这一结果与 H0 的模型、数据、卡数和优化口径均不同，而且当前仓库未保存其原始日志或链接，因此只能支持“不要把 15k 当成天然收敛点”，不能用于推导 H0 的具体终点。

训练计划分为：

| 阶段 | 步数 | 性质 | 决策 |
| --- | ---: | --- | --- |
| H0-A | 0–15k | 与 E0 对齐的必做阶段 | 保留 5k、10k、15k；15k 完成导出和审计 |
| H0-C1 | 15k–25k | 预留的第一续训阶段 | 15k 窗口改善至少 1%，且时间/存储允许时执行 |
| H0-C2 | 25k–40k | 更长续训上限 | 25k 使用同一判据仍改善且无训练健康异常时讨论 |

H0-C 不是在原命令上临时多跑几步。它必须在 H0-A 启动前准备好独立配置和启动入口，并满足：

- 从完整的 15k DCP 恢复 optimizer、scheduler 和 RNG；
- H0-A 的 cosine schedule 在 15k 到达最小倍率 `0.1`，即学习率 `5e-6`；H0-C1 与 H0-C2 均从该值无 warmup、恒定续训；
- 边界测试必须证明 15k 最后一个 H0-A step 与恢复后的首个 H0-C step 都是 `5e-6`，不允许因为把 `max_steps` 改大而重新解释 cosine 曲线；
- H0-A 的 15k checkpoint、FP32 export、收据和日志不可覆盖；
- continuation 使用新的 run/阶段身份，记录父 checkpoint；
- 25k、40k 是累计 global step，而不是在 15k 后重新计数。

H0-C1/H0-C2 已具备独立配置和启动/恢复模式；preflight 会核对父阶段边界、完成标记、基座身份、两卡拓扑、FP32 export、action audit 和实测容量。恒定 `5e-6` scheduler 及“改变 cosine horizon 会导致 LR 跳升”的边界测试已纳入本地测试。它们仍须随 H0-A 一起在目标 2×80G 机器完成真实模型验收；不得直接用 H0-A 的 `--resume` 假装执行 H0-C。

### 6.2 100-step 后冻结六天时间预算

E0 的约 3.24 秒/step 来自最后两层、DDP、batch 32，不能外推到完整 Expert、FSDP2、每步 4 个 microbatch 的 H0。六天排期在目标 80G 机器完成 100-step smoke 之前只是占位计划，不得据此承诺 15k、25k 或 40k 的完成日期。

`--smoke 100` 结束后，必须立即生成时间预算表：

1. 丢弃 step 1–20 的冷启动数据，并排除带 validation 的末步；
2. 对 step 21–99 的 `step_seconds` 计算 median、p90、mean 和样本数；
3. 单独记录总 wall-clock、模型加载、validation、DCP 保存/恢复和 FP32 export 的耗时；
4. 用实测值估算 5k、10k、15k、25k、40k 的到达时间；
5. 加至少 20% 不确定性余量，再重新冻结六天日程。

预算公式为（`S` 为目标累计 step，正式 H0-A 会从 step 0 独立启动）：

```text
T_compute(S)       = S × median(step_seconds[21..99])
T_to_checkpoint(S) = T_formal_setup
                   + T_compute(S)
                   + floor(S / 250) × T_validation
                   + floor(S / 500) × T_checkpoint
T_train_budget(S)  = 1.20 × T_to_checkpoint(S)
```

这里的 `T_validation` 使用一次正式 8-batch validation 的实测耗时，`T_checkpoint` 使用一次完整 DCP 保存的实测耗时。100-step smoke 尚无这两个正式实测值时，必须在预算表中把它们标成“待 step 500 校准”的独立估计，不得悄悄并入 step time。FP32 export、action audit、哈希、传输和首轮评测不进入 `T_train_budget`，统一由末尾 24 小时收尾窗口覆盖，避免重复计时。

[`scripts/plan_h0_timing.py`](scripts/plan_h0_timing.py) 会将 100-step 报告落盘为 JSON 和 Markdown。报告必须包含下表，不能只在终端口头判断“看起来来得及”：

| 目标 | `T_train_budget` | 预计到达时间 | 距租期末余量 | 判定 |
| ---: | ---: | --- | ---: | --- |
| 5k | 待实测 | 待实测 | 待实测 | pilot 里程碑 |
| 10k | 待实测 | 待实测 | 待实测 | pilot 里程碑 |
| 15k | 待实测 | 待实测 | 待实测 | H0-A 必须可达 |
| 25k | 待实测 | 待实测 | 待实测 | H0-C1 预留判断 |
| 40k | 待实测 | 待实测 | 待实测 | H0-C2 预留判断 |

第一次 100-step smoke 尚未覆盖正式 8-batch validation 和 500-step DCP 周期，因此其预算是初版。正式 H0-A 到 step 500 后，必须用第一次真实 validation、DCP 大小与保存耗时更新一次预算；这是早期校准点，不得等到 5k 或训练过半才重排。

六天窗口按 144 小时计算时，至少预留最后 24 小时用于最终导出、action audit、文件校验、传输和首轮评测，并另留 12 小时故障余量。环境与数据准备实际耗时也从训练可用时间中扣除。只有满足以下不等式才承诺对应里程碑：

```text
当前时间 + T_train_budget(目标 step) <= 租期结束 - 36 小时
```

若 15k 不满足，不能把 10k 宣称为完整 H0-A；应延长租期或明确降级为 pilot。若 25k 满足且 15k 达到第 10.2 节的冻结改善阈值，则 H0-C1 是计划内动作，不是临时例外。

## 七、训练前验收门槛

正式 15k 训练开始前，以下步骤必须按顺序全部通过：

| 阶段 | 目的 | 通过条件 |
| --- | --- | --- |
| `--check` | 静态身份与数据审计 | 基座、Qwen、vendor、数据、norm、robot config、配置和磁盘全部一致 |
| `--dry-run` | 启动命令预演 | 输出目录未被复用，不创建文件、不启动训练 |
| `--state-test` | toy DCP 验证 | 两 rank 保存后可在新进程精确恢复 |
| `--smoke` | 10-step 真实链路 | 两卡参与，FSDP2 正常，loss/grad norm 有限 |
| `--smoke 100` | 资源、稳定性与初版排期 | 无 OOM/NCCL hang；输出稳态 step-time 统计和 5k–40k 时间预算 |
| `--resume-test` | 生产恢复链路 | 真实模型 step 1 保存后，新进程恢复并完成 step 2 |

验收必须使用准备进行正式训练的同一台机器、同一环境和同一可见 GPU 拓扑。toy test 通过不能替代真实模型恢复测试；没有 100-step 时间预算表，也不得启动正式 H0-A。

## 八、正式训练与恢复协议

### 8.1 正式运行

- 使用启动器生成唯一 run 目录；
- 禁止复用或覆盖已有正式输出目录；
- 在外层 `screen` 或 `tmux` 中前台运行启动器；
- 保存 source commit、配置 SHA、数据与 norm identity、preflight receipt、训练日志和退出码；
- SwanLab 仅用于记录，不作为唯一证据源。

### 8.2 Checkpoint 策略

- 每 500 steps 写一个 DCP；
- 滚动清理普通 checkpoint；
- H0-A 永久保留 5k、10k、15k；
- 若执行 H0-C，另保留 25k、40k，并保持 15k 父 checkpoint 不变；
- 恢复前要求 checkpoint 存在 `COMPLETED.json`；
- 恢复时核对 frozen base、数据、norm、训练参数选择、模型几何和双卡拓扑；
- 恢复产生新的 `preflight_resume_*.json`，不得覆盖原始收据。

### 8.3 存储门槛

模型和数据准备完成后，H0-A 正式输出文件系统至少保留 120 GiB 可用空间。该门槛只覆盖当前滚动策略、H0-A 的三个永久里程碑、最终约 23.75 GiB FP32 导出和保存临时余量，不自动证明 continuation 空间足够。

首次真实 `--resume-test` 后记单份 DCP 实测大小为 `D`，完整 FP32 导出及临时空间为 `E`。若计划同时在线保留 5k、10k、15k、25k、40k 和一个滚动 checkpoint，continuation 启动前至少按下式重新核算，或先将早期里程碑做逐文件哈希后可靠归档到另一块盘：

```text
continuation working-space target >= 1.20 × (6 × D + E)
```

时间和空间任一项不足，都不得先启动 continuation 再边跑边清理唯一副本。

因此开机选盘时应按上述 continuation 公式预留容量，而不是只按 H0-A 的 120 GiB 下限开盘。若本机无法预留，必须在 H0-A 开始前指定另一块有容量证明的归档盘，并先验证哈希、复制和恢复流程。

## 九、监控与中止规则

### 9.1 必须记录

- optimizer step；
- train loss；
- Clean validation BC loss；
- grad norm；
- learning rate；
- 每步耗时与数据加载耗时；
- 每 rank peak allocated/reserved GPU memory；
- world size 与 global batch；
- checkpoint 保存、清理和恢复事件；
- SwanLab run ID、进程退出码和异常栈。

### 9.2 立即中止

出现以下任一情况，不得让正式 run 带病继续：

- loss 或 grad norm 非有限；
- 只有一个 rank 在工作、rank 间 step 不一致或 NCCL 持续异常；
- trainable inventory 不符合“完整 Expert + projections”；
- VLM/vision 意外解冻；
- 数据、norm、基座或配置 identity 改变；
- checkpoint 无法在新进程恢复；
- 输出盘空间不足以安全完成下一次 checkpoint；
- 为绕过 OOM 临时改变 chunk、动作语义或训练范围。

若 batch 32 在目标 80G 机器上 OOM，先确认 gradient checkpointing 与 FSDP2 包装确实生效。回退配方为 batch 16、accumulation 2，保持 global batch 64；回退后重走 smoke 与真实恢复验收。

### 9.3 不作为提前中止理由

短窗口内 validation BC loss 波动、单个 checkpoint 的临时退化或训练早期收敛较慢，不足以单独停止无异常的正式训练。除明显发散或工程错误外，应保留预定里程碑，让闭环评测依据完整候选作判断。

## 十、选模与效果评测

### 10.1 训练期选模

训练期只允许使用：

- Clean validation BC loss；
- 预先固定的 Clean 小开发集；
- 与训练健康相关的工程指标。

不得根据 Randomized 成绩反复选择训练步数、checkpoint 或超参数。

### 10.2 候选 checkpoint

至少保留并比较：

- 5k：早期候选；
- 10k：中期候选；
- 15k：E0 对齐候选，也是 H0-A 阶段终点；
- 25k：执行 H0-C1 时的第一 continuation 候选；
- 40k：只有 C1 末端仍改善时保留的长训候选。

15k 不是默认的最终候选。为避免看到曲线后临时解释，H0-A 与 H0-C1 共用以下冻结判据。对阶段终点 `S`，定义：

```text
L_old    = median(loss[S-1750], loss[S-1500], loss[S-1250], loss[S-1000])
L_recent = median(loss[S-750],  loss[S-500],  loss[S-250],  loss[S])
relative_improvement = (L_old - L_recent) / L_old
```

其中 loss 仅指同一份冻结 Clean validation 上每 250 step 产生的 BC loss。若 `relative_improvement >= 1.0%`，则登记为“仍有明确改善”；若小于 1.0%，则登记为“平台或证据不足”。1% 是用于资源决策的工程阈值，不是收敛定理；一旦看到正式曲线不得回改。

15k 被登记为“仍有明确改善”、H0-C 工程门槛已通过且时间/存储预算满足时，应按计划进入 C1。25k 使用同一公式决定是否讨论 C2。不得查看 Randomized 后再决定是否续训。如果存储和评测预算允许，可从滚动 checkpoint 中增加一个由 Clean validation 预先选定的候选，但规则同样必须预先冻结。

### 10.3 闭环判定

H0 的主要结论应来自与 E0 对齐的固定任务、固定 seed/scene、相同推理精度和相同成功判定代码。成功标签只认官方任务的 `check_success()` 调用链；人工回放只用于错误分析。

报告至少包含：

- 总成功数与成功率；
- Clean 与 Randomized 分项结果；
- 相对 E0 的逐场景配对变化；
- 每任务结果，而不只报告宏观平均；
- checkpoint、代码、基座、数据和评测环境 identity；
- 失败类型与代表性回放索引。

Randomized 只能在候选与选模规则冻结后用于最终报告。若看过 Randomized 后再次修改训练或重新选 checkpoint，新的结果属于下一轮实验，不能继续记为原 H0。

## 十一、成功、失败与后续决策

### 11.1 工程成功

满足以下条件即可判定训练系统工程成功：

- 2×80G 上完成真实模型 FSDP2 smoke 与恢复；
- H0-A 15k 训练无身份漂移或无法恢复的 checkpoint；
- 5k、10k、15k 里程碑可用；
- 最终 FP32 HF export 完成；
- action audit 通过。

工程成功不等于模型效果成功。

### 11.2 模型效果成功

只有在冻结协议下，H0 相对 E0 呈现可复核的闭环提升，同时没有由少数任务或评测异常造成的虚假增益，才能认为“扩大 Action Expert 容量”获得支持。报告必须同时给出绝对结果和配对差异，不以训练 loss 更低代替闭环证据。

### 11.3 失败后的决策

| 结果 | 解释 | 下一步 |
| --- | --- | --- |
| 工程失败 | 尚未检验主假设 | 修复 FSDP/恢复/资源问题后重走验收，不改实验语义 |
| 工程成功、闭环无提升 | 完整 Expert 本身证据不足 | 回到 E0/H0 对照，优先分析任务级退化和过拟合，不叠加多个新变量 |
| Clean 提升、Randomized 不升 | 容量改善拟合但泛化不足 | 下一轮单独评估一种合规增广或正则化变量 |
| Clean 与 Randomized 都提升 | 主假设得到支持 | 将 H0 作为下一轮基线，每次只加入一个新变量 |
| Randomized 提升但 Clean 明显退化 | 存在权衡或评测噪声 | 检查逐任务配对和选模偏差，不直接宣布总体成功 |

## 十二、明确排除的本轮功能

- 动态 `seen_instructions` 采样；
- photometric、背景替换、干扰物贴图或其他图像增广；
- robot state 噪声；
- VLM 后层解冻与参数组学习率；
- E0/F1 warm start；
- relative action；
- Randomized 数据训练或调参；
- 8 卡训练和跨 world-size 恢复；
- 在线 RL、offline RL、价值加权 BC、ensemble 或 task-specific 路由。

这些方向不是永久否定，而是不进入 H0。未来若启用，必须形成新的实验编号、单独配置、独立验收与对照结论。
